# المرحلة السادسة — لوحة موظفي الدعم الفني

## ما أُضيف

- لوحة إحصائيات لإجمالي التذاكر والجديدة والمفتوحة وقيد المعالجة وبانتظار العميل والتي تم حلها والمغلقة والمسندة للموظف الحالي وغير المعينة.
- جدول يعرض رقم التذكرة والعميل وبريده ورقم الطلب والفئة والحالة والأولوية والموظف المسؤول وآخر تحديث.
- بحث برقم التذكرة أو اسم العميل أو اسم المستخدم أو البريد الإلكتروني أو رقم الطلب.
- مرشحات للحالة والأولوية والفئة، بالإضافة إلى عرض تذاكري المسندة إليّ أو غير المعينة.
- ترتيب النتائج من الأحدث تحديثًا، مع ترقيم صفحات لتقليل البيانات المحمّلة في كل مرة.
- فتح المحادثة من صف التذكرة؛ الإسناد وتغيير الحالة والأولوية متاح من أدوات الموظف داخل المحادثة.
- بقيت إدارة الموظفين وإضافة/تعطيل/إزالة دور الدعم في لوحة المالك فقط، كما كانت في المرحلة الثالثة.

## حماية البيانات

أُضيفت دالة `support_staff_dashboard` بصلاحية `SECURITY DEFINER`، وتتحقق من أن المستدعي موظف دعم فعّال أو مالك قبل إرجاع أي بيانات. البريد والأسماء لا تظهر عبر قراءة عامة لجدول المستخدمين؛ تُعاد فقط عبر هذه الدالة المقيّدة، وتقتصر على حقول لوحة الدعم. العملاء والزوار لا يمكنهم تنفيذها.

## تفعيل التحديث

بعد رفع ملفات المشروع إلى GitHub:

1. افتح مشروع Supabase الحالي ثم SQL Editor.
2. شغّل `supabase/migration_support_6_dashboard.sql` مرة واحدة. الترحيل إضافي وآمن لإعادة التشغيل ولا يحذف بيانات.
3. انتظر نجاح الترحيل ثم حدّث نشر الموقع من GitHub.
4. سجّل الدخول بحساب موظف دعم نشط وافتح `support-inbox.html`.

## التحقق

- فُحصت صياغة JavaScript للوحة، وتحقق وجود الحقول والمعرفات المرتبطة بها.
- لا يمكنني تأكيد نتيجة استعلام SQL أو الصلاحيات على مشروع Supabase المباشر من النسخة المحلية. بعد تشغيل الترحيل، تحقق بحساب موظف نشط، ثم جرّب عميلًا عاديًا وتأكد أن استدعاء `support_staff_dashboard` يُرفض.
- جرّب البحث بأرقام تذاكر وطلبات فعلية وبريد واسم عميل، وكل مرشح، والصفحات التالية. افتح محادثة كتذكرة وتحقق من الإسناد من أدوات الموظف.

لا تتضمن هذه المرحلة إرسال البريد أو الإشعارات الداخلية؛ هذان في المرحلتين السابعة والثامنة.
